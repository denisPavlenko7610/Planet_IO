## Confirmed defect

### P3: kills of an implausible run are added to `TotalKills` and reported to the leaderboard

Files: `Assets/_Project/Runtime/Application/Game/PostRunService.cs:46-47`,
`Assets/_Project/Runtime/Core/Services/ServiceState.cs:31-49`.

Reproduction (EditMode, `PostRunServiceTotalKillsTests.TotalKillsBoard_IgnoresKillsOfAnImplausibleRun`):
finish run 1 with 5 s duration and 90 kills (fails `ScoreValidationRules.IsPlausible`), then run 2 with 120 s and
3 kills.

Expected (GDD 7.2: "a run is reported only if it passes the plausibility check ... kills no faster than one per
2 s plus 3"): the total-kills board shows 3. Actual: 93.

Cause (confirmed by reading and by the test): `OnRunEnded` calls `state.RegisterDeath(...)` before `ReportRun(...)`.
`RegisterDeath` adds all kills to the stored `TotalKills` regardless of plausibility. `ReportRun` returns early for the
implausible run, but the next plausible run reports the inflated stored total. The inflated total is also written into
the cloud save (`CloudSyncService.Capture`) and reported again by `PushPlatformData`.

Impact: limited to leaderboard integrity for client-reported numbers, which GDD 7.2 already treats as best-effort. A
crude cheat that passes one plausible run afterwards can still publish inflated totals. Priority P3.

Fix (applied after separate approval): `ServiceState.RegisterDeath` got a `countKills` parameter (default `true`);
`PostRunService.OnRunEnded` passes `ScoreValidationRules.IsPlausible(info.Summary)`. `RunsFinished` is still counted,
as `OnRunEnded_ImplausibleRunReportsNothing` requires. Consequence to be aware of: kills of a run shorter than 10 s
are not added to `TotalKills`; if the same run id later ends as a plausible run (continue), all its kills are added
once. Regression tests: `TotalKillsBoard_IgnoresKillsOfAnImplausibleRun` and
`TotalKillsBoard_CountsAllKillsOnceTheSameRunBecomesPlausible`. Full EditMode after the fix: 578 of 578 Passed.
PlayMode was not rerun after the fix; the change touches only `PostRunService` and `ServiceState`.

## Hypotheses reviewed

- **Cloud save with a newer `Version` is overwritten.** Confirmed by reading `CloudSaveRules.Merge`: an invalid or
  newer-version cloud save counts as missing, so an older client uploads its local data over it. GDD is silent on
  forward compatibility, so this is a specification gap, not a defect. No test was written to avoid pinning an
  unspecified behavior. Decide the rule before the first save-format change.
- **Upload requested during a running sync waits until the next pause.** `RequestUpload` sets `_uploadPending` but
  `Finish` does not re-check it. Covered by the pause flush; low risk, not tested.
- **`lost / before` in `PlayerFeedbackPresenter.OnDamaged` can divide by zero.** Dismissed by reading:
  `ReportDamageRpc` is sent only when `lost > 0`, so `before > 0`.
- **Music selection with a one-track pool can index out of range.** Dismissed by reading: both pools hold three
  tracks.
- **`RunEndInfo.IsBlitz` is ignored by `PostRunService`.** Blitz runs are reported to the same boards. GDD is silent.
- **Doc drift.** GDD sections 2, 6.3 and 6.4 still list pre-revision numbers (speed 4.8/9.6/3.6, moons 3 hits, 12 s,
  6%, camera exponent 0.28); the code follows the November 17 revision in section 5 (4/8/3, 2 hits, 16 s, 10%, 0.10).
  Section 6.2 still calls the moon reset a known defect although its regressions pass. This is a document sync issue.
