## Confirmed defects

### P2: damaged moons carry over through death into continue

Files: `Assets/_Project/Runtime/Gameplay/Player/Player.Lifecycle.cs`, methods `Defeat`, `ContinueRpc`, `Revive`;
`Assets/_Project/Runtime/Gameplay/Planet/PlanetScale.Moons.cs`, `UnsubscribeMoons` and `RefreshTierServer`.

Reproduction: start solo; set the player's mass to 1.0 (tier III, four moons); destroy moon index 0 with three hits
(mask 14); call `Defeat`; then `ContinueRpc`.

Expected: GDD 6.2 explicitly requires satellites to reset on death. On continue, mass 0.5, tier II, a new set of two
live moons: mask 3.
Actual: mass and tier are right, but the mask is 2; the first moon stayed broken from the previous life. A separate
death-without-continue check also shows the mask staying 3 instead of 0.

Evidence: two Failed results in `playmode-moons.json` with expected and actual masks and stack traces. They are two
manifestations of one defect.
Cause: `_moons.Reset()` is called on network despawn; an ordinary death leaves the NetworkObject in the session.
Changing the slot count on continue keeps the damage of the lower slots.
Minimal fix: reset the moon state separately and publish an empty mask on death; on revive build a set for the new
mass, including the case where the mass did not change. Also check the immunity and knockback timers between lives,
without declaring them defects absent a separate test.
Regressions: `Moons_DefeatClearsSatellites` and `Moons_ContinueDoesNotRetainBrokenMoonFromPreviousLife`. Production
code was not fixed.

### P2: the ad configuration fails the release-readiness contract

File: `Assets/GoogleMobileAds/Resources/GoogleMobileAdsSettings.asset:15`.
Reproduction: run `ReleaseReadinessTests.AdMob_AndroidAppIdIsConfigured`.
Expected: the project's own Android App ID is configured; the existing contract explicitly excludes the demo
`ca-app-pub-3940256099942544~3347511713`.
Actual: the resource holds exactly the demo ID; the test is Failed. A release ad unit is set separately in
`AdMobRewardedService`.
Minimal fix before release: set the App ID of the matching AdMob app and repeat the readiness test plus an SDK check
on Android. A working App ID was not derived from the ad unit and not substituted.
This is a release-configuration readiness defect; a malfunction of real ad display on a device is not proven by this
run.

## Conflicting requirements and remaining risks

- `ProjectConfigurationTests.AndroidRelease_UsesApi37Il2CppAndArm64` requires API 37 while ProjectSettings sets 36.
  This is a confirmed mismatch between the test and the configuration; no evidence was found that 37 is the approved
  product requirement. It is not declared a Google Play requirement violation. An authoritative requirement must be
  chosen before fixing.
- The 0.03 tier hysteresis is set in `TierRules` and pinned by tests, but the GDD 6.2 table lists the plain
  thresholds. This is an undocumented behavior detail, not a proven defect.
- The GDD describes moon placement through "the number of live moons"; the implementation uses a slot count and a
  mask, so gaps remain after a moon breaks. The wording needs clarifying; a regression expectation for redistributing
  moons was not invented.
- A bot's death from moon damage needs a separately agreed scenario: `Enemy` does not override `DeathCheck`. The
  tests executed cover damage but not a moon finishing off a bot. This is a hypothesis, not a confirmed defect.
- The new gravity, perks, leadership and bounty appeared during the check and are not part of the agreed moon-phase
  audit. Their presence does not mean they were verified.
